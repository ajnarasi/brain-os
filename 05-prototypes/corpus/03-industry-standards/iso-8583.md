# ISO 8583 — Financial Transaction Card-Originated Messages

## Overview

ISO 8583 is the international standard that defines the message format and communication flow used by card-based payment systems to exchange electronic transactions between acquirers, card networks (schemes), issuers, and processors. It is the lingua franca of card authorization and clearing: virtually every credit, debit, and ATM transaction on the Visa, Mastercard, American Express, Discover, JCB, UnionPay, Interac, and regional rails traverses an ISO 8583 dialect at some point in its life cycle.

The standard is published by the International Organization for Standardization in three parts — Part 1 (messages, data elements, and code values), Part 2 (application and registration procedures for Institution Identification Codes), and Part 3 (maintenance procedures). There are three major versions of the message format itself: **1987** (the original, still the most widely deployed), **1993** (a revision with additional fields and updated definitions), and **2003** (which extends the element inventory up to 192 data elements but has seen only limited adoption). In practice, most acquirer-to-network and network-to-issuer links still run a network-specific flavor of the 1987 version — for example, Visa Base I / Base II, Mastercard's MIP / Customer Interface Specification (CIS), and the proprietary host specs published by major processors including Fiserv (VisionPLUS, North, Omaha) and FIS.

## Message Structure: MTI, Bitmap, Data Elements

An ISO 8583 message has three structural components:

1. **Message Type Indicator (MTI)** — a four-digit field identifying what the message is.
2. **Bitmap(s)** — a fixed-length field (primary bitmap is 64 bits; optional secondary and tertiary bitmaps extend it to 128 or 192 positions) where each bit indicates whether a given data element is present.
3. **Data Elements (DEs)** — the variable payload, present only when their corresponding bit is on.

### Message Type Indicator

The MTI is a 4-digit number. Each digit is meaningful:

| Position | Meaning | Example values |
|---|---|---|
| 1st | Version | 0 = 1987, 1 = 1993, 2 = 2003 |
| 2nd | Message class | 1 = Authorization, 2 = Financial, 3 = File actions, 4 = Reversal/Chargeback, 5 = Reconciliation, 6 = Administrative, 7 = Fee collection, 8 = Network management |
| 3rd | Message function | 0 = Request, 1 = Request response, 2 = Advice, 3 = Advice response, 4 = Notification |
| 4th | Message origin | 0 = Acquirer, 1 = Acquirer repeat, 2 = Issuer, 3 = Issuer repeat, 4 = Other |

So `0100` is a 1987-format authorization request from an acquirer, and `0110` is its response. `0420` is an acquirer-originated reversal advice.

### Bitmap

The primary bitmap is 8 bytes (64 bits) encoded as binary or 16 hexadecimal characters. Bit 1 of the primary bitmap, when set, indicates a secondary bitmap follows — extending the addressable field range to 128. Each remaining bit position N means "data element N is present in this message."

### DE3 Processing Code

DE3 is a 6-digit code split into three 2-digit subfields: **Transaction Type** (positions 1-2), **From Account** (positions 3-4), and **To Account** (positions 5-6). Common transaction types include `00` (goods/services purchase), `01` (cash withdrawal), `09` (purchase with cashback), `20` (refund), `30` (balance inquiry), and `31` (credit/payment).

### DE22 POS Entry Mode

DE22 conveys how the card and PIN were captured. Common PAN entry values include `01` (manual), `02` (magnetic stripe), `05` (ICC/chip with CVV), `07` (contactless EMV), `80` (fallback from chip to stripe), `81` (e-commerce), `90` (magnetic stripe read, full track), and `91` (contactless magstripe).

## Message Flows

**Authorization (0100 / 0110)** — The acquirer sends a `0100` request to the issuer via the network. The issuer responds with a `0110` containing DE39 (response code) and DE38 (auth code) if approved. No money moves; funds are earmarked.

**Financial / Purchase (0200 / 0210)** — Used on networks that combine authorization and posting (common on debit/ATM). The `0200` immediately debits the cardholder account.

**Reversal (0400 / 0410 / 0420 / 0430)** — A reversal is sent when a prior authorization must be undone (timeout, partial completion, customer cancellation). `0400` is a request, `0420` is an advice (acquirer-initiated, no issuer reply required beyond 0430).

**Chargeback / Dispute (1420 or 1442 in 1993 format)** — Issuer-initiated messages that return a transaction to the acquirer with a dispute reason code. The clearing dialect (Visa VCMS, Mastercard MDS/IPM) defines the reason-code tables.

**Reconciliation / Settlement (0500 / 0510 / 0520 / 0522)** — End-of-day totals messages used to close the batch and reconcile acquirer and issuer positions before funds settlement.

## Relationship to Card Networks and Processors

ISO 8583 is a base standard; **every major network publishes its own dialect** by fixing element subfields, adding private-use data elements, and defining the bitmap layout and encoding (ASCII, EBCDIC, BCD, binary). Examples include Visa's VIP/Base I, Mastercard's CIS / IPM, Discover's Dial, American Express's GNS, and processor host interfaces from Fiserv (Omaha, North, VisionPLUS), FIS, Global Payments, and Worldpay. Switches and gateways that sit between merchants and networks typically speak several of these dialects at once and translate among them.

## Relevance to the Fiserv Brain Demo

The Fiserv Brain concept is a per-merchant reasoning layer sitting above a card-acceptance platform. ISO 8583 is the substrate it must understand: when a transaction declines, the Brain's explanation to the merchant depends on mapping DE39 response codes to merchant-readable causes and next actions; when retries are proposed, DE3, DE22, and DE55 determine whether an SCA-exempt retry is even viable; when chargeback prevention is discussed, DE37 (RRN) and DE42 (MID) are the keys used to reconcile clearing records. A Brain that cannot read and reason about 8583 fields cannot explain payments to a merchant in a grounded way — so this standard is foundational corpus for the prototype.
