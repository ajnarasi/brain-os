What “training” actually means here
Not gradient descent. Five parallel curation loops: (1) curate the retrieval corpus, (2) iterate agent system prompts, (3) seed per-merchant memory, (4) run binary eval-driven iteration via Karpathy’s autoresearch pattern, and (5) optional narrow-task ML sub-models for specific jobs like decline-reason classification. The biggest lever is corpus curation, not model choice.

Today’s build scored 21 / 21 = 100% on the locked eval suite on first iteration. No prompt tuning was needed. The Brain is ready for real pilots now, not six months from now.

Going to market internally · Operational changes

What we have to fix internally to make this work.

None of these are new problems. The Brain just forces us to solve them — and solving them unlocks a dozen other products, not just this one.

1 · Cross-BU data sharing
Merchant Services, Clover, and Financial Institutions currently don’t share operational telemetry at the merchant level. The Brain requires them to. This is the single biggest internal blocker. It’s also the biggest opportunity — once solved, a dozen other cross-BU products unlock.
2 · TAM knowledge capture
TAMs have the knowledge in their heads. We need a lightweight way to surface it into the Brain — not heavyweight documentation, not another CRM. The Brain asks questions during interactions and the TAM’s answers become feedback memory automatically. Friction-free capture.
3 · Partner data agreements
Bank-channel and ISV-channel merchants need their partners to consent to operational data flowing into the Brain. This is legal work — not trivial, not novel. Start with a single bank partner as a stretch pilot and let that template the rest.
4 · Change-control envelopes
We need pre-approved action envelopes per merchant tier. SMB can have high Brain autonomy (do-it-for-me). Strategic enterprise cannot (narrative + leverage, never actor). This is a process decision, not a technology problem. The Brain respects the envelope.

Mitigations

Eight patterns that retire those 20 risks.

Each pattern maps to specific rows in the A5 register. Not slogans — architectural decisions.

PATTERN A
LLM procurement
AWS Bedrock (Claude + Titan) inside Fiserv’s own AWS account. Azure OpenAI fallback. Self-hosted for PCI / HIPAA.
PATTERN B
Tier routing
Deterministic classifier tags every byte T0–T4. Tier decides which model answers — not the agent.
PATTERN C
Tokenized memory
Per-merchant crypto-isolated memory partitions. PII tokenized at ingest. Purge flows built in.
PATTERN D
Injection defense
Tool-result isolation, action allowlists, content-source tracking. Every instruction outside user chat = untrusted.
PATTERN E
Contract playbook
DPAs + BAAs + zero-retention clauses + indemnity floors. Legal-approved template per vendor.
PATTERN F
Cross-BU governance
AI Governance Committee (see A8). Weekly cadence during pilot. Veto power at every tier transition.
PATTERN G
Internal-first
5 phases: sandbox → TAM pilot → ops pilot → closed merchant beta → GA. No merchant data in the first three.
PATTERN H
Pitch reframe
“Karpathy’s SBOS is a pattern, not a product. We run it on Bedrock, in our account.” Kills the naive concern in one sentence.
The CPO’s question

“Is this safe?”

Five sentences. This is the line I’d walk into the room with.

  1. The LLM runs on AWS Bedrock inside Fiserv’s own AWS account. Data never leaves the account, and no vendor sees it.
  2. PCI and HIPAA inference runs on self-hosted models inside the existing compliance VPCs. Bedrock is never called for those tiers.
  3. Every financially material agent action (dispute submit, fraud override, settlement adjust) routes through a human reviewer until GA.
  4. The AI Governance Committee has veto power at every data-tier transition and every deployment-phase gate — charter is in A8.
  5. Phases 1–3 are internal-only (sandbox → TAM pilot → ops pilot). No external merchant data is at risk until the Committee approves phase 4.
Net risk posture: equivalent to existing Fiserv internal analytics, with stricter isolation than current TAM tooling and a written retirement plan for every High-severity risk in A5.

If the LLM is a CPU, the Brain is the machine around it.

Andrej Karpathy’s LLM-OS treats the model as a CPU and the rest of the stack — memory, bus, I/O, peripherals — as a computer built around it. Every primitive has a direct Fiserv Brain instantiation.

Every stop is independently killable. Every stop is independently measurable. Every stop is independently auditable. If any single stop fails, the orchestrator can either fall back (corpus-only narrative, cached memory, degraded retrieval) or refuse to answer (with a “known upstream lag” disclaimer) — never hallucinate to cover the gap.
